## Decisions (locked)
- **Ring buffer:** caller-owned, drop-newest. A full buffer returns `EventStatus::BufferFull` and bumps a drop counter. Drop-oldest is a consumer-side policy. `EventLoop` does not hold `Arc<RingBuffer>`. (Replaces the spec's "SPSC + drop oldest".)
- **`WindowEvent` is strictly `Copy`.** Text/IME use fixed inline buffers (e.g. 32-byte UTF-8, chunked when longer).
- **Multi-window** per `EventLoop`. **IME** deferred to Phase 3, API-ready now. **Clipboard** deferred to tpt-archon.
- **Spec correction:** "xdg-shell v5" is wrong. v5/v6 were unstable revisions, obsolete since wayland-protocols 1.12. Target stable `xdg_wm_base`, bind min(compositor, latest). Verify the version in Phase 3.
- **Sibling repos (found via the org page):** [tpt-archon](https://github.com/tpt-solutions/tpt-archon), [tpt-visual](https://github.com/tpt-solutions/tpt-visual) (facade crate `tpt-av-visual`), [tpt-nova](https://github.com/tpt-solutions/tpt-nova), [tpt-appfront](https://github.com/tpt-solutions/tpt-appfront), [tpt-shell](https://github.com/tpt-solutions/tpt-shell). Local stub types stay until the real APIs are matched.
- **Event API details:** `poll_events`/`step` take `&mut self`; `Window::raw_*_handle()` return `Result`; `YieldPoint` is emitted by `EventLoop`; the facade provides `new_event_loop()` instead of `EventLoop::new()`. See spec.txt section 12.
- **Event signing (archon bridge):** Ed25519 (`ed25519-dalek`, BSD-3-Clause, allowed by deny.toml). The router holds the secret key; applications verify with the public key only, so they cannot forge events. Each signature covers the window id, a per-window sequence number and a canonical encoding of the event. The sequence must increase, which rejects replay and reordering.
- **Capability mapping (archon bridge):** a window's events are `Resource::Channel(window id)`. The owner needs `Read` on it, an input source needs `Write`. `InputScope::Global` also needs `Read` on `Device(INPUT_DEVICE)`, and `DisplayScope::Any` needs `Read` on `Device(DISPLAY_DEVICE)`. `OwnAndChildren` and `WindowAndChildren` are rejected rather than granted, because child routing is not designed yet.
- **Key repeat:** a held key sends repeated `KeyboardInput::Pressed` events (text included), as on Win32. There is no `repeat` flag, so the event cannot tell a repeat from a new press. Implemented on X11 (detectable auto-repeat) and Wayland (sctk repeat timer).

- [x] **Decided: archon capabilities.** Map window scopes onto archon's `Resource::Channel` / `Resource::Device` capabilities inside `tpt-window-archon`; do event signing there as an envelope (core stays crypto-free). Extend archon only if the mapping cannot express per-window scope.

- [x] **Decided: transparency belongs to the renderer.** The window layer cannot make a window see-through by itself (measured: DWM alone gives white). It needs a DXGI composition swapchain with composite alpha in the GPU code. Deferred to the renderer work.

## Phase 4: Capability & Compositor (Weeks 9–12)

Findings: a capability is an unforgeable `(Resource, Right)` token, revocation is checked at every enforcement point, and there is no signing, so signing lives in tpt-window's bridge.

- [x] Verify signed input events (spoofing prevention): Ed25519, verified with the public key only. Tests: an altered event fails, an altered window id or sequence fails, an event signed by another key fails, a replayed or reordered event is rejected, and an event copied to another window fails. **Open:** the signing key is currently passed in by the caller; the tpt-archon key store that should hold it is not wired.
- [x] Display-server protocol in `protocol.rs`: **wire format v1 and version handshake** (in core, no I/O, tested).
- [x] Shared-memory transport (decided above): `tpt_window_core::channel::FrameRing` is safe Rust over a `RingMemory` trait (5 tests: order, wrap-around over 50 000 frames, full ring refuses without changing state, corrupt length detected without moving the consumer, minimum size). `tpt-window-shm` implements `RingMemory` over a named Windows file mapping, with the atomics and unsafe confined to that crate (3 tests: a producer and consumer on two separate views of the mapping, 50 000 frames in order; duplicate names refused; a too-small mapping refused). - [x] Capability-gated input routing tests: `tpt-window-archon/tests/routing.rs` (9 tests) runs the router against a mock authority that follows archon's `CapabilityIssuer` semantics (liveness on every check, `ReadWrite` covers both rights). ### B. Winit blockers and API (later)
- [~] Modifier state: `WindowEvent::ModifiersChanged(ModifiersState)` is sent by Win32, wasm, X11, Cocoa and Wayland, cleared on focus loss, and encoded in archon's signed bytes. Win32 is tested with injected Shift (`tests/modifiers.rs`). Not done: a key-repeat flag, and the Wayland path is CI-only.
- [~] Runtime setters: `Window::set_min_size`, `set_max_size`, `set_resizable`, `set_maximized`, `set_minimized` (physical pixels) as `WindowCommand`s. Win32 does all five and is tested against the system's own queries (`IsZoomed`, `WS_THICKFRAME`). Cocoa does all five (compile-checked). X11 does limits, resizable and minimize, and maximize is still a no-op (needs `_NET_WM_STATE`). Wayland does limits, maximize and minimize; resizable is not expressible. wasm ignores them. Also `set_decorations` and `set_fullscreen`: Win32 does both (tested: the title bar goes and comes back with the client size kept; fullscreen covers the display and restores the size), Cocoa does both (`styleMask` and `toggleFullScreen`, compile-checked only). X11 and Wayland do not yet. `set_always_on_top` does Win32 (`HWND_TOPMOST`, tested against the topmost style) and Cocoa (window level, compile-checked only). Not done: title and icon (the title already has a setter via `WindowCommand::SetTitle`), and X11 and Wayland for always-on-top, decorations and fullscreen.
- [~] Cursor: `Window::set_cursor_visible` on Win32 (`WM_SETCURSOR`; tested against `GetCursor`), wasm (CSS `cursor`), X11 (a blank cursor from an empty bitmap) and Cocoa (`NSCursor` hide and unhide, counted globally). X11 and Cocoa are compile-checked only. Not done: Wayland (no-op), grab and lock, icon, set position. Grab: `Window::set_cursor_grab(CursorGrab::{None, Confined, Locked})`. Win32 clips the pointer to the client area while focused (tested against `GetClipCursor`), and `Locked` also hides it. X11 uses `XGrabPointer`, and web uses pointer lock for `Locked` (not `Confined`). Cocoa and Wayland accept it and do nothing. Icon: `Window::set_icon(Option<Icon>)` (`Icon::from_rgba` checks the length). Win32 sets it (tested through `WM_GETICON`), X11 sets `_NET_WM_ICON`; Cocoa, Wayland and web accept and ignore it.
- [~] File drop: `WindowEvent::FileDropped` and `FileHovered` carry a path in chunks (`continued` until the last), and `FileHoverCancelled`; `PathAssembler` rebuilds a path. Win32 reports drops (`DragAcceptFiles`, tested by the chunking unit tests, not by a real drop); Win32 does not report hover, which needs `IDropTarget`. Not done: hover on Win32, and drops on X11 (XDND), Cocoa and web. Theme and monitors: `Window::theme()` and `ThemeChanged` on Win32 (tested); `available_monitors()` and `current_monitor()` on Win32 (tested), Cocoa (`NSScreen`), X11 (root screen) and web (`window.screen`). Theme on web: `prefers-color-scheme` with a change listener, removed on drop, reported once at creation and on change (compile-checked). Theme on Cocoa is not reported yet.
- [~] `HasWindowHandle` / `HasDisplayHandle`: `tpt_window::SurfaceTarget::new(&window)` implements both, so wgpu's `create_surface` takes it without `create_surface_unsafe` (tested on Windows). Not done on `Window` itself: core forbids `unsafe_code`, and the trait cannot be implemented for `Window` from the facade (orphan rule), so the newtype is the route.
- [~] Full key table: added NumLock, ScrollLock, PrintScreen, Pause, Menu, F13-F24, IntlBackslash, and the media and volume keys (`KeyCode` is `#[non_exhaustive]`, so this is additive). Mapped on Win32 and wasm, and on X11 and Wayland through the shared evdev table. Not mapped on Cocoa, where these keys still report `Unidentified`. archon's signed key tags have rows for them (100 onward). Not verified with a real keyboard.
- [~] `EventLoopProxy` (`tpt_window::EventLoopProxy`, `Send` and `Clone`) with `wake()` and `request_exit()`. Win32 wakes the loop with a thread message (tested across threads, including a 10 s wait that ends after 100 ms). Other backends have no wake yet, so the loop notices the proxy only at its `step` timeout. User events: `EventLoopProxy::send_user(u64)` reports `WindowEvent::User` in send order, and keeps the rest queued when the caller's queue is full (tested on the headless backend). ### D. Differentiators (later)
- [x] Deterministic record/replay: `tpt_window_core::record` (`Recorder`, `read_log`, a versioned format) over the canonical codec (`tpt_window_core::codec`, moved from archon with the same bytes and a decoder for every variant). `tpt_window_test_utils::replay` rebuilds a recording as a headless loop frame for frame. The `record_replay` example records a real Windows session and replays it. `Recorder` is driven by `record_queue` after each poll rather than wrapping `EventSink`, which keeps the frame boundaries.
- [x] Signed, tamper-evident session logs: `tpt_window_archon::session_log`. Each record's Ed25519 signature covers its sequence number, the previous signature, and its bytes, under a domain separator. An authenticated end record makes a log cut at a record boundary detectable. Tests cover a changed byte, a wrong key, a dropped record, truncation at every length, and trailing bytes.
- [x] AI-agent harness on yield points: `tpt_window_archon::harness::AgentHarness` routes the loop's events through the capability router, receives them back verified, and cuts them into `AgentFrame`s at the yield points, each with a window snapshot. Input from the agent goes through the router and is signed. Limit: the router has one inbox per window, so the agent reads back its own input on its next observe. A per-source inbox is the fix and is not built.
- [~] Capability-gated input products: the three products are described in the archon crate docs, and each is backed by a test: view-only tokens (a read-only capability cannot send input), sandboxed plugin windows (no global input without the input device), and revocable remote control (a revoked source is refused at once). No separate product crate is shipped; the building blocks are the product.
- [x] Test-harness upgrade in `tpt-window-test-utils`: `inject_at(frame, window, event)`, `frame()`, `exit_after(frame)`, `captured_commands()` (the commands the application sent), a scripted display list (`set_monitors`), `assert_events!` (patterns in order, then no extras), `scenarios` (DPI change, two displays, moving between displays), and `strategies` behind the `proptest` feature (generated events round-trip through the codec). Frame-stepping is by poll: one poll is one frame.
- [x] Protocol tap and a memfd transport: `tpt_window_core::tap` records the messages that cross a ring (`Tap::observe`) and decodes a byte dump frame by frame (`describe_stream`), without touching the ring. `tpt-window-memfd` implements `RingMemory` over `memfd_create` and `mmap` for Linux, with a cross-mapping test. The memfd crate is compile-checked from Windows (stub `pkg-config` is not needed for it); its tests run in CI only.

## Open Risks
- tpt-archon has no window/input capability concept; tpt-shell is not a compositor (see Needs your decision). The bridge maps scopes onto the existing `Channel`/`Device` resources, so no archon change is needed for that. The tpt-archon adapter and the signing-key store still need writing there.
- WASM backend: verified in Chromium for input and resize. Firefox and Safari are not verified.
- Win32 `real_window` failed about 1 run in 3 when run alone (11 of 30). The cause was the zero-allocation assertion: the system sends `WM_SETTINGCHANGE` during the test, and the theme read allocated two `Vec`s there. The read now uses stack buffers. It passes 30 of 30 after the fix, and the hot-path assertion still holds. IME composition reads no longer allocate. - Win32 `raw_input` failed once in a full run and passes 30 of 30 alone. The test sums relative mouse motion and checks its direction, so physical mouse movement during the run can break it. Keep the machine still during the run, or make the test read only its own injected motion.
- Linux and macOS checks are CI-only now (WSL Ubuntu removed). The last Linux run predates the shared-memory and ECS work and the manifest moves (core and raw-window-handle are now gated to the platforms that use them). Those changes are type-checked for Windows only, so the first CI run after a push is the real check.
- Cocoa, the Wayland key-repeat path and the Win32 IME composition with a real input method are compiled but not run end to end.
- The vsync test (`tpt-window-sys-win32/tests/vsync.rs`) needs DWM composition and a real refresh. It skips when composition is off. A CI VM may pace differently, so a failure there means the test's rate bounds need a look, not necessarily the backend.
- `Window` getters take a `Mutex` per read; fine for now, revisit if benchmarks vs winit show it matters
- Weeks 5–8 for three hard platforms is aggressive
- `windows-rs` compile times
